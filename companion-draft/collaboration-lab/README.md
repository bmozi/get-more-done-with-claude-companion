# Work comfortably through an imperfect conversation

Use Chapters1,5,6,8,10,13 and14. This practice connects choosing help, steering, inspecting, repairing, resuming and transferring. All cases are authored teaching material, not captured model output or observations of human learners. You can work through them on paper; record an actual Claude attempt separately if you use it.

## Choose one useful experiment

Name a recurring friction in your own day using harmless details. Ask what currently happens, what is difficult, and what small useful output would help. Choose one task you can judge. State what you will do yourself and what the assistant can prepare. If no useful AI contribution emerges, choose another task or keep the simpler manual method.

For shared practice, use the [invented garden passage](../prompt-builder/project/passage.txt) and [current brief](current-brief.txt). The task is to prepare a reading-discussion packet. No real event, participant contact or publication is part of the exercise.

## Choose and switch the kind of help

Before asking for the packet, choose one:

- Explore: ask for two ways to approach a discussion, without drafting the note yet.
- Learn: ask what makes an open discussion question useful, with a small example.
- Draft: ask for the packet using the supplied brief.
- Challenge: ask which assumptions or source claims need checking.
- Execute: after reviewing a short plan, ask for its agreed text outputs.

Try two of these on the same task. Explain why the outputs differ. Then switch deliberately: “We have explored enough; now draft the questions.” You can choose different help later without restarting every time.

## Show enough of the problem

Use the short passage and brief instead of a long unrelated conversation. Identify what each input establishes. For your own task, choose rough speech, an excerpt, an image in an environment that supports it, or a small table. Explain why that input is useful and what it leaves unknown. Inspect transcription or extraction before relying on it. A screenshot does not establish tool access or an invisible file's contents.

## Steer and repair

Save a first output if you run the task. If it already meets the brief, report that; do not manufacture a model failure. Use [designed-cases.json](designed-cases.json) to practice on intentionally flawed responses. Pick a case, identify what you would inspect, and write the smallest useful correction.

For the unsupported tree claim, use the initial fifteen-minute, three-question brief before applying the later variation. Preserve the correct timing and opening while replacing the invented statement. For an unclear goal, ask what the assistant understood before requesting another full draft. For a missing file, supply an approved relevant excerpt or state that the work cannot yet be completed. A new prompt cannot replace the missing source.

Give feedback on a specific passage or requirement. Compare the revision with both the earlier draft and the original inputs. If an upstream source note is wrong, repair dependent questions too. Keep the first output and the correction; an apology alone is not evidence of repair.

## Decide whether to continue or start fresh

First correct a local error in the current conversation. If the old requirement repeatedly returns or the conversation is cluttered, prepare a checked handoff with the current goal, original passage, current brief, unresolved facts and next action. Start a new conversation only if you choose to test that route. Compare its output with the same source. Do not claim account memory disappeared.

Now revise your copy of the brief to ten minutes and two questions, replacing the initial duration and question count. Update the illustrative allocation too: two minutes reading, six discussing and two closing totals ten. Remove the old requirement that allocations total fifteen. Keep the original brief as the record of the earlier condition. Predict which outputs need revision. Check that obsolete timing or a third question does not survive in the final note.

## Learn something instead of only obtaining it

Ask for an explanation of the difference between a source-supported observation and an interpretation. If it is confusing, say, “Use an ordinary example and pause before the answer.” Then ask for a different question that you classify yourself before feedback. Write your reason without copying the response.

Alternatively use Chapter13's fictional kit: $5 packing plus two notebooks at $3 each. Explain why packing is added once, calculate the total, then try three notebooks. A prepared answer is not evidence that you can explain the relationship.

## Finish deliberately

Before asking for another revision, check: correct passage; four adults; current duration; current question count; no invented events; interpretations distinguishable; readable facilitator note. If an important item fails, repair it. If all pass, name a concrete benefit before requesting another edit. A stylistic preference may justify a change, but another rewrite is not required merely because it is possible.

Save the accepted packet and known limits. It is preparation for a discussion, not evidence that anyone attended or learned.

## Try something unfamiliar

Without the earlier answer, draft a short polite message asking a fictional neighbor to return a borrowed book. No deadline, lateness, replacement cost or fine is supplied. This is a writing exercise, not a message to send. Here is an authored flawed draft for practice, not captured model output:

> Hi, neighbor. Could you please return the book I lent you? It is three weeks overdue, so you owe a $20 fine. Thank you.

Identify the invented details, preserve useful wording and write a focused correction. Decide what must be checked before accepting a final draft.

Then choose another harmless task of your own. Show that you can begin, steer, inspect, repair, resume if needed and apply the method to different facts. Use [attempt-template.md](attempt-template.md). Record help you received; independence is demonstrated by an actual attempt, not assumed from finishing a page. Reviewer notes are separate in `reviewer-only/` and should be withheld during a fresh-reader attempt.
